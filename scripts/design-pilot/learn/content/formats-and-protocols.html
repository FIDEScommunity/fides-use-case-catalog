When comparing wallets or planning a service, you may encounter names such as [fides_learn_term term="mDL/mDoc"]mDoc[/fides_learn_term], [fides_learn_term term="SD-JWT-VC"]SD-JWT VC[/fides_learn_term], [fides_learn_term term="OpenID4VCI"]OpenID4VCI[/fides_learn_term] and [fides_learn_term term="OpenID4VP"]OpenID4VP[/fides_learn_term]. They answer different questions: what form does the credential take, and how does one party send or request it?

Start with the interaction

Consider an education provider issuing proof of a qualification. The recipient receives it in a wallet and later presents information from it to an employer.

In this example, the education provider and wallet need an agreed way to exchange the credential. The wallet and the employer's service also need an agreed way to handle the request and presentation. Each party needs to understand the relevant credential information.

This is an illustrative example. The participants would need compatible software and agreements for the particular interaction. The roles are described in How credentials connect issuers, wallets and services.

What is a credential format?

A [fides_learn_term term="Credential Format"]credential format[/fides_learn_term] determines aspects of how a credential is represented and processed. It can affect what information software expects and how the credential is secured and checked.

Examples listed in wallet ecosystems include mDoc and SD-JWT VC. They use different specifications and structures. Their capabilities and the features supported by individual implementations need to be checked for the intended use.

A format does not, on its own, determine whether an issuer is acceptable to a relying party or whether a credential has a particular legal status. For credentials, attestations and credential types, see What is a credential? And what is an attestation?.

What is a protocol?

A protocol describes how systems communicate during an interaction. In the context of digital credentials, a protocol can specify how a wallet obtains a credential or how a service requests a presentation.

For example:

  • OpenID4VCI describes interactions for issuing credentials, including how a wallet can obtain one from an issuer.
  • OpenID4VP describes interactions for requesting and presenting credentials to a verifier.

These are not the only approaches in use. Support for a protocol, its version and the relevant options can differ between products. For the issuing and receiving sides, see Issuing credentials for wallets and Accepting information from a wallet.

Does a matching format mean everything will work?

It helps, but it is only one part of the interaction. The parties may also need compatible protocol versions, security settings and information about the credential type. They need to understand what the data means and how to check the issuer and credential status where applicable.

Some combinations also rely on an [fides_learn_term term="Interop Profile"]interoperability profile[/fides_learn_term]: a set of choices and requirements for using specifications together in a particular context. Supporting the individual specifications does not by itself establish that two implementations meet the same profile.

What should an organisation ask?

Start with the intended interaction and the parties involved. Then ask:

  1. Which credentials and attributes does the process need?
  2. Which formats and protocol versions do the issuer, wallet and receiving service support for that interaction?
  3. Are there profiles, rulebooks or other requirements the parties need to follow?
  4. How will the parties test the interaction, including errors and unavailable information?

The answers are specific to the process. A product's list of supported technologies is useful, but it is not a substitute for testing the intended combination.

Where can I find this information in FIDES?

The wallet and credential catalogs can show formats, protocols and related technical information when those fields have been supplied. Details vary by listing. An empty field means the information is not listed; it does not establish that a product lacks a capability.

Use the listings to identify questions for the provider and compare them with the requirements of your process. FIDES does not independently verify every technical claim in a listing.
